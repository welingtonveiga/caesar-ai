# Caesar v1 Specification

## Overview

Caesar is a personal AI agent that runs as a single long-lived process on your own machine and talks to you over Telegram. Version 1 delivers the **chat core**: one agent, one channel, a custom LangGraph brain, sandboxed code execution, long-term memory behind a swappable abstraction, and human-in-the-loop (HITL) approval for dangerous actions.

The project has two goals that shape every decision below: it must be **genuinely useful daily**, and it must serve as a **learning lab** for LangGraph, long-term memory strategies, and agent architecture. The repo is public on GitHub under the MIT license, but Caesar is a personal tool first — polish for third-party installers is not a v1 concern.

This document records the v1 decisions, the rationale behind them, and the alternatives that were rejected. It supersedes [brainstorm.md](brainstorm.md) for anything they disagree on.

## Audience

- Primary reader: the author, as the reference while building v1.
- Secondary readers: GitHub visitors who want to understand the design.
- Assumes familiarity with Python, asyncio, and LLM tool-calling; LangGraph specifics are explained where they matter.

## Goals

- A Telegram-driven agent useful enough to interact with every day.
- A custom-built LangGraph brain, so the graph structure itself is the learning exercise.
- Safe autonomous execution: sandboxed code, tiered tool governance, explicit approval for irreversible actions.
- A memory module isolated behind a narrow interface, so memory backends can be swapped and compared without touching the engine.

## Non-Goals (deferred to v2+)

Each deferred feature keeps an architectural seam in v1 so adding it later is an extension, not a refactor:

- **Multi-agent support** — the config loader returns a list of agents; v1 requires the list to have exactly one entry.
- **Multiple channels with shared context** — channels implement a common adapter interface; v1 ships only Telegram.
- **Proactive idle behavior** (check-ins, suggestions) — nothing in v1 initiates contact except replies and task-completion reports.
- **Skills folders** (Claude skills format).
- **Third-party tool plugin API** — v1 tools are built-in only.
- **Docker sandbox backend and the cloud-box deployment** — the sandbox runs behind a `SandboxRunner` protocol; v1 implements only Apple Container, which makes v1 macOS-only.
- **Telegram group chats** — v1 is direct messages only.
- **PyPI-only egress filtering for the sandbox** — v1 sidesteps the need for it (see Sandbox).

## System Overview

Caesar is one async Python process with four components, matching the brainstorm's component model:

| Component | Responsibility |
| --- | --- |
| Channels | Adapters between messaging platforms and the brain. V1: Telegram. |
| Brain | The LangGraph engine: receives messages, plans, calls tools, enforces tiers, manages tasks. |
| Actuators | Built-in tools: file reads, web reads, workspace writes, sandboxed code execution. |
| Memory | Long-term memory behind a two-method interface. Default backend: LangMem. |

Everything runs on a single asyncio event loop. The Telegram listener, LangGraph invocations (`ainvoke`), and background tasks are all async; each promoted task runs as an `asyncio.Task`. A task paused at an approval breakpoint consumes no resources — its state lives entirely in the SQLite checkpointer, so the engine stays free for other work.

### Process lifecycle

Caesar runs as a plain foreground process (`caesar run`). Supervision — respawn on crash, start on boot — is delegated to the operating system: launchd on macOS, systemd on Linux. Caesar contains zero self-daemonization logic and ships example launchd/systemd unit files instead.

*Rejected:* self-daemonizing (reimplements what launchd/systemd do well, with worse edge cases) and running Caesar itself in Docker (complicates local filesystem access and Apple Container sandboxing).

## Agent Definition

An agent is a directory. V1 resolves exactly one agent directory, in priority order:

1. CLI argument: `caesar run <dir>`
2. `CAESAR_AGENTS` environment variable
3. `./agent.yml` in the current directory

Scanning subfolders for agent definitions (from the brainstorm) is dropped from v1: it is the only genuinely complex discovery mode and it creates ambiguity about which agent owns the channel.

### Agent directory layout

```
my-agent/
├── agent.yml          # config: name, model, folders, channels
├── soul.md            # personality, identity, tone (free-form prose)
├── .env               # secrets (gitignored; .env.example ships in the scaffold)
├── filesystem/        # the agent's own file area (default folder access)
├── workspace/         # per-task working directories: workspace/<task-slug>/
└── memory/
    ├── current.db     # engine-owned working state (see Persistence)
    └── long-term.db   # memory backend's exclusive storage
```

### Configuration (`agent.yml`)

- **Name** — defaults to `Caesar`.
- **Model** — a LangChain `init_chat_model` string such as `anthropic:claude-sonnet-5`, plus optional parameters (temperature, max_tokens). Any LangChain-supported provider works, which makes cross-model comparison a one-line YAML change. Default: a current Anthropic Sonnet-class model (good tool use, mid cost for an always-on agent).
- **Folders** — the list of host folders the agent may access beyond its own directory. Defaults to none beyond `filesystem/`.
- **Channels** — v1 supports only `telegram`, which requires a bot token and a user-ID allowlist.

### Secrets

`agent.yml` never holds raw secrets. Values reference environment variables with `${VAR}` interpolation (for example `token: ${TELEGRAM_BOT_TOKEN}`), and Caesar auto-loads a `.env` file from the agent directory. Config stays committable; secrets stay local; a future cloud deployment is just "set env vars".

*Rejected:* inline secrets (one careless `git add` leaks keys) and a custom `secrets.yml` convention (`.env` is universal and tooling speaks it natively).

### Soul

`soul.md` holds the agent's identity, tone, and values as free-form prose — editable like a character sheet. The engine composes the final system prompt: engine-owned scaffolding (tier and approval behavior, task conventions, memory instructions) is always present and wraps the soul, so personality can never disable safety behavior. The scaffold ships a default soul: a capable, dry-witted aide-de-camp named Caesar.

*Rejected:* soul as a YAML field (multi-paragraph prose in YAML is miserable) and soul-as-entire-prompt (every author must re-state the tier protocol correctly or governance silently degrades).

## Brain

### Graph design

The brain is a hand-built LangGraph `StateGraph`, not the prebuilt ReAct agent:

```
agent node → tier router → tools node → agent node → … → end
                 │
                 └─ Tier 3 → interrupt() → checkpoint to SQLite → await approval
```

Tier 1 and Tier 2 tool calls flow straight through to execution. A Tier 3 call hits `interrupt()`, checkpoints the thread, and halts until the channel delivers an approval. Building this graph by hand is deliberately part of the learning goal: the governance model is an explicit, visible edge in the graph rather than a callback buried in someone else's abstraction.

*Rejected:* `create_react_agent` (fastest to a working bot, but governance ends up expressed through configuration rather than structure) and "prebuilt now, custom later" (the rebuild would touch checkpointing and HITL — the exact parts that are painful to migrate with live task state).

### Conversation vs. tasks

The conversation is the default mode: one LangGraph thread per channel chat, handling ordinary back-and-forth inline. Conversation history is trimmed or summarized to stay within context; long-term continuity comes from the memory module, not the thread.

The brain **promotes** a request to a task only when it involves sandbox execution, multi-step tool work, or will outlive a single reply. A task gets:

- a short slug ID (for example `csv-cleanup`),
- a working directory at `workspace/<slug>/`,
- its own graph thread, checkpointed independently,
- background execution as an `asyncio.Task`, keeping chat responsive.

Task completions and failures are reported back into the originating chat. That is a reply to an earlier request, not proactive behavior.

The promotion decision is an LLM judgment call and will need tuning against real usage — this is a known risk, accepted in exchange for keeping casual chat free of task ceremony.

*Rejected:* every request is a task (matches the brainstorm verbatim but buries one-line answers in ceremony) and user-declared tasks only (pushes bookkeeping onto the user and prevents the agent from learning to manage its own work structure).

## Tool Governance

### Tiers, classified by blast radius

V1 reframes the brainstorm's tiers around **reversibility** rather than locality:

| Tier | Policy | Contents |
| --- | --- | --- |
| 1 | Autonomous, immediate | All reads — local files and web fetch/search — plus writes strictly inside `workspace/` and `filesystem/`. |
| 2 | Autonomous, sandboxed | Code execution inside an isolated container. |
| 3 | Requires approval | Any mutation outside Caesar's own folders: sending messages, writes to other configured host folders, deletes, destructive host operations. |

The reframing exists so that research-style work (read files, fetch pages, save intermediate results) never interrupts the user, while approval friction is reserved for irreversible effects.

*Rejected:* treating web reads as Tier 3 (an assistant that asks permission for every URL stops being used within a week) and treating all writes as Tier 3 (tasks could not save intermediate files, and sandbox output mounts would be pointless).

### HITL approval flow

When a task hits a Tier 3 breakpoint, Caesar posts an **approval card** to Telegram: the task slug, the exact action payload (the email draft, the shell command, the target path), and Approve/Reject inline keyboard buttons. The button callback carries the task ID, so approvals stay unambiguous even with several tasks paused.

**Nothing typed in chat can ever count as approval.** The graph resumes only on the button callback; natural-language "go ahead" gets a reply pointing at the buttons. This keeps an LLM interpretation step out of the last line of defense.

*Rejected:* `/approve <slug>` text commands (tedious on a phone, typo-prone) and natural-language approval (puts an LLM judgment exactly where the governance model demands determinism).

## Sandbox (Tier 2 execution)

### Runner

Code execution goes through a `SandboxRunner` protocol — roughly `run(code, in_dir, out_dir, limits) → result` — with **Apple Container** as the only v1 backend. Choosing the younger runtime is a deliberate learning-lab trade: if its mounts or networking fight back, the escape hatch is a Docker implementation of the same protocol, not a redesign. Docker also remains the path to a Linux cloud deployment later.

Mount discipline follows the brainstorm: the task's input directory mounts read-only (`in/`, code can never corrupt seed files); the output directory mounts read-write (`out/`, the only place results can land).

### Network policy: prebaked image, no network

Containers run with networking **fully disabled**. The sandbox image ships with a pinned set of common packages preinstalled (pandas, numpy, openpyxl, pillow, matplotlib, beautifulsoup4, and similar). When a task needs a package that is missing, the run fails gracefully, the agent reports which package it needed, and the user adds it to the image.

This decision replaced the brainstorm's "outbound access to PyPI only" because that guarantee **cannot be expressed by the container runtime alone**: Docker offers per-container network on/off and subnet-level rules, not domain allowlists; PyPI sits behind Fastly's rotating CDN ranges, so IP allowlisting is brittle; Apple Container has no egress filtering hooks at all. Every real "PyPI only" setup adds a filtering proxy — extra security-critical infrastructure.

Disabling the network entirely is also the stronger posture: exfiltration from the sandbox becomes structurally impossible, and the supply-chain risk moves from "whatever the LLM decides to `pip install` mid-task, whose build hooks execute with network access" to a package list vetted once at image-build time.

*Rejected:* two-phase install-then-isolate (the install phase itself runs arbitrary build hooks with network — a real hole) and a filtering proxy in v1 (meaningful infrastructure on the least mature part of the stack; still exposed to malicious packages hosted on PyPI itself). A proxy remains a candidate v2 experiment if missing packages become a daily annoyance.

## Memory

Memory is the primary research area, so v1's job is to make the boundary clean, not the backend clever.

### Interface

The brain sees exactly two operations:

- `recall(query, k)` → relevant memory snippets, called while building the prompt for a turn or task.
- `observe(messages)` → fire-and-forget; the backend extracts and stores whatever it deems worth keeping. Runs in the background after turns complete.

All intelligence — what to store, deduplication, decay, profiles versus facts — lives behind the interface. That is precisely what makes swapping LangMem for a homegrown experiment a clean A/B comparison.

The default backend is **LangMem** (extraction plus semantic search) persisting to `memory/long-term.db`.

*Rejected:* rich typed memory (profile/entities/episodes as first-class interface types — the taxonomy hardens into the interface and every future backend must implement it) and agent-driven memory tools (`save_memory`/`search_memory` calls — recall quality then depends on the model remembering to remember, and passive accumulation never happens).

## Persistence

All durable state lives in two SQLite databases inside the agent's `memory/` folder, named for the short-term/long-term memory metaphor:

- **`memory/current.db`** — engine-owned working state: LangGraph checkpoints (including paused HITL threads), the task registry (slug, status, workspace path), and channel bookkeeping.
- **`memory/long-term.db`** — owned exclusively by the memory backend.

**Boundary rule:** the memory abstraction only ever touches `long-term.db`. A memory experiment must never require migrating `current.db`; replacing the memory backend must never risk live task state.

*Rejected:* one combined database (memory experiments would share a file with live checkpoints) and a database per concern (four connection pools for a personal tool is ceremony without payoff).

## Telegram Channel

- **Library:** python-telegram-bot v21+ (async-native, first-class inline keyboards, the most documented option — friction stays low while attention is on LangGraph).
- **Transport:** long polling. No public endpoint, no TLS certificates, identical behavior on a laptop and a future cloud box. *Rejected:* webhooks (require a publicly reachable HTTPS endpoint — a tunnel, on a local install).
- **Access control:** `agent.yml` must list allowed Telegram user IDs; the channel refuses to start without the list. Messages from anyone else are logged and **silently dropped** — no reply, so strangers probing bot handles learn nothing. This is the right posture for an agent with filesystem access and code execution behind it. *Rejected:* polite refusal replies (confirms to a prober that the bot is live) and first-contact pairing codes (a v2 nicety, with a subtle first-boot race).
- **Scope:** direct messages only in v1.

## Project Conventions

- **Package:** `caesar-ai` (the name `caesar` is taken on PyPI; reserve `caesar-ai` early with a stub upload). CLI command: `caesar`.
- **Tooling:** uv + `pyproject.toml`, Python 3.12+, ruff, pytest.
- **Distribution:** GitHub-only while the API churns — `uv tool install git+https://github.com/<owner>/caesar`. Publish to PyPI once v1 stabilizes. The "single dependency" promise holds: one install command pulls everything except the container runtime.
- **License:** MIT — zero friction for anyone learning from or forking the project, and the default in the Python agent ecosystem.

## V1 Acceptance Test

V1 is done when the following works end-to-end from a phone over Telegram:

1. Send: *"Take the CSV in filesystem/, clean it up and give me a summary — and save the cleaned file to my Documents folder."*
2. Caesar promotes the request to a task (slug + `workspace/<slug>/`), reads the CSV (Tier 1), and runs the cleanup in an Apple Container sandbox with no network (Tier 2).
3. The write to `~/Documents` — outside Caesar's folders — pauses the task on an approval card with inline buttons (Tier 3).
4. On approval, the file lands in Documents and the summary arrives in chat.
5. After a Caesar restart the next day, asking about the CSV shows the interaction was retained (memory recall).

One scenario, every layer proven.

## Risks and Open Questions

- **Task promotion is an LLM judgment call.** The chat-versus-task boundary will misfire early on and needs tuning against real usage. Mitigation: log every promotion decision; adjust the scaffolding prompt as patterns emerge.
- **Apple Container is the youngest tool in the stack**, holding the most security-sensitive job. Mitigation: the `SandboxRunner` protocol keeps a Docker fallback one implementation away.
- **Prebaked-image package misses** could become a recurring annoyance. Mitigation: graceful failure with a named missing package; revisit a filtering proxy in v2 if the friction is real.
- **Open question:** how much conversation history to keep in the thread before summarizing, and whether summaries should feed `observe()` — to be settled empirically once memory is wired up.
